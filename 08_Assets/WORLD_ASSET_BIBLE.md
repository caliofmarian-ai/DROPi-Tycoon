# DROPi Tycoon World Asset Bible

## Purpose

This document is the canonical world-art and asset-production specialization for DROPi Tycoon.

It translates the existing Universe, Business, Logistics, Game, World and UI canon into one coherent visual-production system.

It does not redefine gameplay, economy, logistics, persistence or technical authority.

Authority chain:

`VISION -> UNIVERSE_DESIGN -> BUSINESS_DESIGN -> LOGISTICS_DESIGN -> GDD / World / UI specializations -> WORLD_ASSET_BIBLE`.

This document was explicitly authorized by the Project Owner on 2026-09-07 in `09_Development/Owner_Directives/2026-09-07_MASTER_OWNER_DIRECTIVE_003_WORLD_ART_AND_ASSET_SYSTEM.md`.

---

# 1. Canonical Visual Identity

The production visual direction is:

**Stylized 3D Pre-Rendered Mobile World — premium mobile tycoon art with soft-isometric / elevated 3/4 presentation, clear three-dimensional volume, readable materials, consistent soft lighting, controlled color, strong object recognition and mobile-first legibility.**

The current owner-approved candidate asset board establishes the seed visual direction.

Quality may improve toward richer three-dimensional presentation, but the project must not silently switch to an unrelated art style.

This direction does not require a full real-time 3D engine rewrite.

The authoritative Phaser runtime may use pre-rendered/cached 2D textures and sprite atlases that visually represent three-dimensional assets when that is the best performance trade-off.

---

# 2. Style Invariants

Every production family must respect these invariants unless a later explicit Owner Directive supersedes them.

## Perspective

- soft-isometric / elevated 3/4 family;
- consistent camera logic inside each runtime class;
- no arbitrary mix of frontal cartoon art, photorealistic renders, flat icons and incompatible isometric styles;
- directional assets must remain readable for gameplay movement and world placement.

## Lighting

- soft, readable key lighting;
- controlled ambient occlusion / contact shadow feeling;
- enough contrast to separate forms without darkening mobile readability;
- consistent light direction within a production family;
- no cinematic lighting that obscures gameplay information.

## Materials

Materials should be recognizable at gameplay scale, including:

- metal;
- glass;
- concrete;
- asphalt;
- timber;
- cardboard;
- textile;
- plastic;
- water;
- vegetation;
- painted vehicle surfaces;
- stone/brick where appropriate.

## Color

DROPi identity supports:

- bright blue/cyan for technology, routes and product identity;
- green for growth, success, community and nature;
- gold/orange for value, reward and premium emphasis;
- deep blue for contrast and support surfaces.

These colors are identity anchors, not a requirement that every object be blue/green/orange.

Cities, companies, people, vehicles and nature require broad controlled color diversity.

# 12. Asset Scale Strategy

The target is a governed library capable of growing into thousands of assets without becoming unmaintainable.

Canonical production model:

**Master Family -> Controlled Variants -> Runtime Derivatives.**

Examples:

- `human_courier` -> multiple identities/outfits -> walking/vehicle/portrait derivatives;
- `building_residential_euro` -> multiple structures/materials/tiers -> footprint/direction derivatives;
- `tree_urban_deciduous` -> species/size/season variants -> optimized world textures;
- `product_fresh_food` -> product variants -> parcel/pallet/storefront/inventory derivatives.

The project should prefer meaningful variation over creating thousands of nominally different files with negligible visual distinction.

# 13. Runtime Dimension Contracts

Art generation must follow implementation contracts rather than inventing arbitrary dimensions.

## Current Exact Contracts

| Runtime class | Current contract |
|---|---|
| Courier transport atlas | 448 x 896 transparent atlas; 4 x 8 cells; 112 x 112 per cell |
| Courier atlas directions | down, left, right, up; four animation frames each; repeated for carrying/non-carrying state |
| Ambient citizen walking atlas | 256 x 256; 4 x 4 cells; 64 x 64 per frame |
| Static ambient citizen | 64 x 64 |
| Residential/shop building source footprint derivative | 138 x 156 current cached texture target |
| Depot/industrial building source footprint derivative | 164 x 156 current cached texture target |
| HQ exterior derivative | 208 x 176 current cached texture target |
| Tree family target | 96 x 104 current cached texture target |
| Smartphone/UI icon master | 96 x 96 source recommended; normally rendered around 48 x 48 or responsive equivalent |
| HQ/Marketplace scene | 1200 x 720 logical scene; modular props normally 64–256 px class rather than one flat background |

These contracts describe the current runtime and may evolve only through deliberate technical/runtime changes.

## Future Large Infrastructure Rule

Airports, rail stations, ports, ships, aircraft, large industrial complexes and future world-scale infrastructure do **not** receive arbitrary final pixel dimensions before their runtime footprint, camera, collision, layering and culling contract exists.

They should first be defined as a modular family and then exported to the exact dimensions required by the implementation slice.

This prevents wasted art and oversized mobile textures.

# 15. Naming

Names should encode function and family clearly.

Preferred pattern:

`<domain>_<family>_<variant>_<state>_<tier>.<ext>`

Examples:

- `human_courier_female_07_walk_down.webp`
- `building_shop_pharmacy_modern_03.webp`
- `vehicle_van_delivery_blue_02.webp`
- `product_food_bread_crate_01.webp`
- `tree_urban_deciduous_large_04.webp`
- `rail_freight_container_car_03.webp`

Avoid meaningless names such as `final_new_2.png`.

# 16. Candidate vs Approved vs Runtime

Asset state must be explicit.

## Candidate

Generated or imported for evaluation.

A candidate is not automatically allowed in the live game.

## Approved Source

Owner/project-approved art source or family reference.

## Production Asset

Finalized source prepared according to the style and dimension contract.

## Runtime Asset

Optimized derivative actually loaded by the game.

A runtime asset should be traceable to its production/approved source.

# 17. Quality Gates

Before runtime integration, an asset family must be checked for:

- canonical fit;
- style consistency;
- diversity quality;
- correct function/product meaning;
- dimensions and anchor/collision compatibility;
- transparency/background requirements;
- compression/readability;
- Android memory/performance impact;
- naming/provenance;
- no accidental duplication of approved branding;
- owner visual quality when material.

Issue #317 remains the cross-cutting visual-quality gate.

Issue #327 owns city/world visual convergence.

Issue #332 owns courier/vehicle/management art convergence.

Issue #406 owns playable-vision convergence.

The dedicated world-asset production umbrella created from this Bible coordinates those existing issues rather than replacing them.

---

# 18. Performance and Simulation Boundary

The asset library may be huge; the active scene must remain bounded.

Rules:

- thousands of repository assets do not mean thousands of simultaneously active objects;
- load/cull by active location and scene;
- reuse atlases and modular textures where practical;
- cache stable visuals;
- avoid giant full-world bitmaps;
- keep high-frequency animation counts bounded;
- protect the Android performance baseline.

The universe can be visually rich without rendering the entire universe at once.

---

# 19. Audio Boundary

Audio remains part of the overall asset system, but this Bible primarily governs visual/world art.

Audio categories such as ambience, vehicles, logistics feedback, UI, weather and music require their own production execution and copyright/provenance controls.

Visual production must not claim audio completion.

---

# 20. Canonical Production Principle

The asset program exists to make the already-canonical world visible.

Art should help the player understand:

- who lives and works here;
- what each company does;
- what products are produced and moved;
- what a city needs;
- where goods are stored and transferred;
- which transport modes are active;
- how a company and city are changing;
- why logistics matters.

---

# Canonical Rule

**DROPi Tycoon world art must represent one coherent stylized 3D pre-rendered mobile society with genuine human, natural, architectural, product and regional diversity. The repository may grow to thousands of assets, but production must remain governed by reusable families, exact runtime contracts, visible economic meaning, Android performance and one consistent visual language from the smallest parcel to the largest port.**
