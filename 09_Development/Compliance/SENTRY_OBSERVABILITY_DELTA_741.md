## Purpose

Record the privacy/data-flow delta introduced by PR #741 without overstating service-wide compliance, Android behavior, Sentry project policy, or external legal approval.

This file is engineering/compliance evidence only. It is not a legal opinion, a Google Play Data Safety submission, a privacy-policy approval, or evidence that every future Sentry event is anonymous.

## Hosted browser correlation metadata

PR #741 adds two non-secret build/deployment identifiers to hosted `game-web` Sentry events when Railway provides valid values at Docker/Vite build time:

- `RAILWAY_GIT_COMMIT_SHA` -> Sentry `release` and `dropi.commit`;
- `RAILWAY_DEPLOYMENT_ID` -> Sentry `dist` and `dropi.deployment`.

The client accepts the commit identifier only when it is exactly a 40-character hexadecimal Git SHA and accepts the deployment identifier only when it matches the expected UUID form. Invalid values are omitted.

These fields are deployment/diagnostic metadata generated by Git/Railway, not user-entered profile data and not application authentication credentials. They are nevertheless transmitted to and processed by Sentry when an event is sent, so they belong in the diagnostic data-flow inventory.

`SENTRY_AUTH_TOKEN` remains server-side administrative/API authentication material. It is not declared as a Docker build argument, is not converted to a `VITE_*` variable, and must not enter the browser bundle, public artifact, event payload, or diagnostic output.

## Error telemetry settings preserved

PR #741 does not enable performance tracing, Session Replay, profiling, feedback UI, or an Android-native Sentry SDK.

Source-enforced browser options remain:

- `sendDefaultPii=false`;
- `tracesSampleRate=0`.

These settings reduce data collection but do not prove that every diagnostic event contains no personal data. Error messages, URLs, breadcrumbs, browser/request context, or service-side network metadata can still be privacy-relevant depending on the event and Sentry configuration.

## Sentry project scrubbing evidence already observed

The post-deploy controlled verification associated with #733 observed the following project settings through authenticated, read-only Sentry API evidence:

- `dataScrubber=true`;
- `dataScrubberDefaults=true`;
- `scrubIPAddresses=false`.

The controlled synthetic event used for that verification did not contain an observed event-level IP field or user-email field. That single event does **not** prove that future events cannot contain or be associated with IP/network or other personal data.

Therefore the current truthful boundary is:

- server-side default data scrubbing: **observed enabled**;
- default scrubber set: **observed enabled**;
- project IP-address scrubbing: **observed disabled**;
- universal anonymity of future telemetry: **NOT ESTABLISHED**.

Changing `scrubIPAddresses` or other Sentry project settings is an external service configuration action and is not silently claimed by PR #741.

## Read-only unresolved-issue inventory

PR #741 adds `game-web/server/sentry-issue-inventory.mjs` and `npm run diagnostics:sentry-issues` for bounded operator diagnostics.

The inventory is intentionally outside the HTTP server route graph:

- it is not imported by `server/server.mjs`, `server/session-authority.mjs`, or `server/runtime-authority.mjs`;
- it performs one authenticated Sentry `GET` request for unresolved issues;
- it caps returned issues at 25;
- it does not resolve, delete, mutate, assign, or comment on Sentry issues;
- it does not print response bodies on permission failure;
- it suppresses network exception text;
- it redacts common email, URL, and token-like strings from issue title/culprit summaries before output;
- it never prints `SENTRY_AUTH_TOKEN` or `VITE_SENTRY_DSN`.

A successful software test of this CLI is not evidence that production has zero unresolved issues. A production issue inventory becomes evidence only after execution with the deployed server-side credentials and recording of the bounded result.

## Android / Google Play boundary

Railway build metadata and hosted-browser Sentry configuration do not prove that the final signed Android AAB contains the same DSN or telemetry behavior. Conversely, a local bundled runtime does not by itself prove that an SDK cannot make off-device network requests.

Final Android privacy, manifest, permission, network, SDK, Play Data Safety, retention/deletion and processor conclusions remain gated on exact-AAB and deployed-service evidence. Do not generalize this hosted-browser delta into a final Android or legal-compliance claim.
