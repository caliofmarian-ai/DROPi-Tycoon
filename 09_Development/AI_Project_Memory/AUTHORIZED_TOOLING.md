# DROPi Tycoon — Authorized External Project Tooling

## Purpose

This bootstrap companion records the Project Owner's standing authorization for AI agents to use connected paid external capabilities when useful to DROPi Tycoon work.

The durable decision authority is `D-TOOLS-001` in `09_Development/AI_Project_Memory/DECISIONS.md`. The applicable canonical authorities include `07_UI/VISUAL_DESIGN_SYSTEM.md`, `00_Project/THIRD_PERSON_OPEN_WORLD_VISUAL_EXPERIENCE_CANON.md`, and the DT-23 truthful visual-classification documents.

## Authorized tools

### Figma

Authorized for in-scope work including:

- UI/UX exploration and review;
- mobile screen layouts;
- HUD, menus and interaction surfaces;
- reusable components and design-system work;
- prototypes and flow validation;
- visual specifications;
- supported design-to-implementation handoff.

### Canva

Authorized for in-scope work including:

- presentations and pitch material;
- campaign and social assets;
- promotional layouts;
- launch/store presentation material;
- communication-oriented visual production derived from approved project truth.

### Runway

Authorized for in-scope work including:

- cinematic and motion exploration;
- bounded image/video generation or editing;
- storyboard, shot and transition prototyping;
- target-film and marketing asset production under DT-23 truth rules;
- approved visual-source derivatives with recorded provenance.

### Higgsfield

Authorized for in-scope work including:

- bounded image, video and motion exploration;
- visual concept and asset-candidate generation;
- controlled 3D/scene experiments when they support an approved DT mission;
- marketing creative variants under DT-23 truth rules;
- approved visual-source derivatives with recorded provenance.

## Standing Owner authorization

Ordinary in-scope use of Figma, Canva, Runway or Higgsfield does not require a new Project Owner approval each time when it stays within an existing subscription/credit allowance and an assigned DT mission.

This standing authorization does **not** authorize:

- new gameplay, economy, architecture, account, monetization, legal, world or release truth;
- transfer of ownership between DT lanes;
- bypass of DT-13 legal/provenance requirements;
- bypass of DT-19 asset governance;
- bypass of DT-14 release evidence;
- bypass of DT-23 truthful creative/public-claim boundaries;
- treating an external design workspace as repository-backed canonical authority.
- creating a second DROPi Tycoon codebase, gameplay runtime, website authority or project authority in an external tool;
- abandoning, replacing or fragmenting the canonical GitHub repository;
- purchasing credits, top-ups, upgrades, subscriptions, accounts or services without explicit Project Owner approval.

## Authority rule

`EXTERNAL TOOL ARTIFACT != CANONICAL PROJECT AUTHORITY`

The GitHub repository `caliofmarian-ai/DROPi-Tycoon` is the single source of truth for code, runtime implementation, canonical documents, contracts, asset manifests, validation and integration history. External workspaces may hold editable working material, but they do not become a parallel source of project truth.

All generated or edited code must enter GitHub through the normal branch, Pull Request, CI and DT-00 audit workflow. Any external artifact selected for implementation or release evidence must be exported or referenced and then governed through the applicable repository provenance, legal, asset and release workflows.

Runway/Higgsfield/Canva/Figma presentation output is never `AUTHENTIC GAMEPLAY` merely because it resembles the target. Only an exact verified runtime capture may receive that classification. Cinematic or generated target material remains `CINEMATIC / NON-GAMEPLAY`, or another truthful non-gameplay classification owned by DT-23.

## Canonical workflow

`GITHUB CANON -> EXTERNAL TOOL WORK -> GOVERNED EXPORT/HANDOFF -> GITHUB PR -> CI -> OWNER/DEVICE EVIDENCE WHEN REQUIRED -> DT-00 MERGE`

Reuse an existing DROPi Tycoon workspace/file when practical. A new external working file is permitted only when the assigned task genuinely needs it; it must map back to an Issue/PR/canonical contract and must not become a separate product repository or deployment authority.

## Fresh-agent rule

A fresh DT agent that may benefit from design, communication, cinematic or asset tooling should read `D-TOOLS-001` and the applicable canonical domain document before using Figma, Canva, Runway or Higgsfield. Tool access is a capability; it does not expand the agent's ownership boundary.
