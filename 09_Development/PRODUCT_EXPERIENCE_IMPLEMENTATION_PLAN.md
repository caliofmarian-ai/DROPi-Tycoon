# Product Experience Implementation Plan

## Purpose

This document turns the newly approved product-experience direction into an executable sequence without discarding already completed Phase-2 systems.

---

# Immediate Hold

PR #288 / RBATCH-022 Vehicle Catalog and Purchasing remains valid work but should not be merged until the current mobile management surfaces receive the first visual-experience remediation.

The purpose of the hold is to avoid multiplying the same temporary panel style across additional systems.

---

# Stage 1 — Canonical Foundation

Establish:

- global-game independence from real DROPi availability;
- reality-inspired simulation rules;
- human-centered company simulation;
- three-perspective consequence design;
- optional future DROPi training bridge;
- mobile-first visual system;
- owner functional and visual verification as separate gates.

Primary documents:

- `00_Project/PRODUCT_EXPERIENCE_PRINCIPLES.md`
- `00_Project/PRODUCT_EXPERIENCE_CANONICAL_ADDENDUM.md`
- `07_UI/VISUAL_DESIGN_SYSTEM.md`

---

# Stage 2 — Employee Experience Reference Surface

Use the Employees scene as the first production-quality management reference surface.

Goals:

- correct current Android clipping and oversized empty panels;
- introduce recognizable candidate/employee visual identity;
- compact the mobile layout;
- show role, status, and only decision-relevant information;
- preserve the authoritative hiring, onboarding, payroll, and Save behavior from RBATCH-018;
- do not invent deep employee mechanics that are not yet implemented.

The first candidate card should demonstrate the design system without hard-coupling the UI to a single permanent candidate.

---

# Stage 3 — Existing Management Surface Remediation

Apply the same visual language to:

- Company Management navigation;
- Financial Report;
- Customer Reviews.

Acceptance includes real Android portrait and landscape owner review.

---

# Stage 4 — Resume Vehicle Fleet

After the reference management surfaces are accepted, update/rebase PR #288 and apply the same visual language to Vehicle Fleet before merge.

Vehicle presentation should support recognizable vehicle identity and clear purchase/ownership state while preserving RBATCH-022 game logic.

---

# Stage 5 — Deeper Human Simulation

Only after the visual foundation is stable, expand employee simulation incrementally through future planned work such as:

- richer candidate variation;
- experience and progression;
- onboarding effects;
- performance history;
- equipment/vehicle assignment;
- satisfaction and retention where justified;
- promotions and role evolution;
- employee-linked customer feedback;
- departure or termination consequences.

Each mechanic must be grounded in understandable causes, player decisions, and company consequences.

---

# Verification Rule

After every merged player-visible change:

1. allow Railway production deployment to update;
2. tell the owner exactly where to navigate;
3. state what changed;
4. state what to test;
5. request real-device screenshots when visual judgment matters;
6. classify the result separately as functional PASS/HOLD and visual PASS/HOLD;
7. remediate before multiplying a rejected visual pattern.
